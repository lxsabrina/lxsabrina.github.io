## 摘要

OpenAI 在 2026 年 7 月把全双工语音模型 GPT-Live 放进 ChatGPT，9 月以 GPT-Live-1 的名字开放 API。它最受关注的是"能同时听和说"，但从工程角度看，更值得注意的是另一个设计：**语音模型只负责对话，推理、工具调用和业务动作通过 delegation（委托）交给后端**，后端既可以是 OpenAI 托管的模型，也可以是开发者自己的 Agent（Client Delegation）。

这个设计把语音智能体清晰地切成三层：

**Voice Interface → Agent Runtime → Business Execution**

Voice Interface 负责理解和沟通，Agent Runtime 负责决策和工具执行，Business Execution 负责真实的业务结果。语音只是交互层，一个语音智能体的商业价值，最终取决于背后的 Agent 能不能把任务正确地完成。

本文围绕五个问题展开：

| # | 问题 |
|---|---|
| Q1 | 什么是全双工？它和传统的轮流式语音系统差在哪？ |
| Q2 | GPT-Live 把哪些事情交给了后端？ |
| Q3 | Client Delegation 的数据流是怎样的？ |
| Q4 | 为什么要拆成三层？每层各负什么责任？ |
| Q5 | 为什么说这比单纯的端到端语音模型更有战略意义？落地要解决哪些问题？ |

## 核心结论

- **全双工解决的是"像人一样对话"**：输入和输出在同一时间轴上并行，模型能附和、被打断、在用户补充时继续听，这是轮流式级联系统结构上做不到的。
- **GPT-Live 刻意不做"万能模型"**：它把推理和工具交给后端，自己专注于实时对话，后端可以按任务难度替换。
- **Client Delegation 把控制权交还给开发者**：上下文、执行和返回内容都由你的应用掌握，代价是你要自己维护对话状态、处理"说了什么"和"做了什么"的一致性。
- **业务价值在下面两层**：语音层决定体验，Agent Runtime 和 Business Execution 决定任务是否真的完成、是否合规、是否可追溯。
- **语音模型正在变成一个入口**：同一个语音层可以连接不同的业务 Agent，这让语音智能体从"一个模型"变成"一个平台"。

## Q1：什么是全双工？

### 结论

全双工是指智能体能**同时听和说**。用户说话时它可以附和"嗯"，它说话时用户可以随时插话或补充，模型对进出两路音频一起推理。GPT-Live 用单个模型处理这些情况，而不是靠外部的语音活动检测去切换"该谁说"。

### 轮流式与全双工的区别

![图 1：半双工与全双工的对话时间线](/img/posts/gpt-live/02-duplex-timeline.svg)

*图 1：上半部分是传统的级联系统，必须等用户说完，经过识别、推理、合成才开口，插话往往被当成噪声或导致硬切；下半部分是全双工，附和、插话、后台任务都在同一时间轴上并行。*

传统语音智能体大多是 ASR → LLM → TTS 的级联结构，本质上是轮流说话：

- 必须判断"用户说完了没有"，判断早了会抢话，晚了会冷场；
- 智能体说话时听不见或不理会用户，被打断时要么说完，要么硬切；
- 背景噪声、"嗯""对"这类附和，容易被误判为新的一轮输入。

全双工把这些问题放进一个模型内部处理。据 OpenAI 公布的数据，语言学习应用 Speak 的早期评测中，打断次数相比之前的轮流式系统减少了近 80%；在 Full Duplex Bench 上比上一代 GPT-Realtime-2.1 高出 30 个百分点，轮次切换的延迟明显下降。这些是厂商自己的数字，但方向很清楚。

### 直接听一听

文字很难传达全双工的感觉。OpenAI 的 [GPT-Live-1 发布页](https://openai.com/index/introducing-gpt-live-1-in-the-api/) 靠上方有一个 **"Try GPT-Live-1"** 的试用区，可以直接和模型进行一段限时的纯语音对话（需要同意 OpenAI 的使用条款和隐私政策）。建议试几件事：

- 在它说话时突然插话，看它怎么接；
- 说一句话停顿一下再补半句，看它会不会抢话；
- 在有背景噪声的环境里说话，或者故意沉默一会儿。

这几下比任何文字描述都更能说明全双工和轮流式的区别。

## Q2：GPT-Live 把哪些事情交给了后端？

### 结论

GPT-Live 只做三件事：听、说、决定什么时候委托。推理、工具调用由后端完成；权限、确认和业务记录由你的应用负责。

### 三个角色

根据 OpenAI 的开发者文档，一个基于 GPT-Live 的系统有三个角色：

| 角色 | 职责 |
|---|---|
| GPT-Live | 处理口语对话：听、说，决定何时把任务委托出去 |
| 后端（模型、Agent 或服务） | 处理委托的任务，调用工具，返回结果供 GPT-Live 说出 |
| 你的应用 | 校验权限、获取用户确认、执行访问你自己系统的函数、保存任务进度 |

在 ChatGPT 里，遇到联网搜索或较难的推理时，GPT-Live 会把问题交给更强的模型在后台处理（上线时是 GPT-5.5），自己继续和用户说话，等结果回来再自然地融入对话。

### 两种委托模式

创建会话时选定委托模式，之后不能切换，要换只能新开会话：

| | Responses Delegation | Client Delegation |
|---|---|---|
| 后端是谁 | OpenAI 托管的 Responses 模型 | 你自己的模型、Agent 框架或服务 |
| 配置 | `delegation.type = "responses"`，指定模型、指令、工具等 | `delegation.type = "client"`，可选 `acknowledgement_delay_ms` |
| 托管工具 | 联网搜索、文件搜索、代码解释器等自动执行 | 全部由你处理 |
| 自定义函数 | 你的应用执行并回传结果 | 你的应用执行 |
| 上下文 | OpenAI 在语音层和后端之间传递 | 你自己维护 |

发布页建议的组合是：高频简单任务配快速模型，复杂问题配强推理模型；也可以接第三方模型。计费上，语音层按分钟计费（每分钟 0.05 美元），后端模型和工具另算。

## Q3：Client Delegation 的数据流是怎样的？

### 结论

Client Delegation 下，GPT-Live 只告诉你"需要委托了"，**不告诉你任务是什么**。你的应用要自己从转写流里拼出对话上下文，交给自己的 Agent，再把结果分成"可以说的"和"只是事实"两类追加回语音层。

### 事件时序

![图 2：Client Delegation 的事件时序](/img/posts/gpt-live/03-client-delegation-sequence.svg)

*图 2：用户、GPT-Live、你的应用、你的 Agent Runtime 四条泳道。*

关键环节：

1. **维护上下文**：应用持续接收 `session.input_transcript.delta` 和 `session.output_transcript.delta`，自己拼成完整的对话记录。这些增量没有轮次结束事件，怎么切分轮次由应用决定。
2. **委托开始**：收到 `session.delegation.created`，里面有委托 ID 和 `target: "client"`，但没有任务文本。
3. **等待期间**：GPT-Live 可以在一段延迟（`acknowledgement_delay_ms`）后自动说一句应答，比如"好的，我查一下"。如果不想要这句话，在延迟到期前发一个空的 `session.thinking.append` 即可；任何 thinking 或 commentary 追加都会取消待发的应答。
4. **执行**：应用把上下文交给自己的 Agent，完成推理、工具调用和业务规则判断。
5. **回传结果**，有三种追加方式，每次不超过 500 个 token：

| 事件 | 含义 |
|---|---|
| `session.commentary.append` | 希望 GPT-Live 说出来的内容，它可能会换个说法 |
| `session.thinking.append` | 供后续回复参考的事实，到达时不会立刻说出 |
| `session.instructions.append` | 会话级的指导，通常不绑定具体委托 |

6. **确认**：对应的 `session.*.appended` 回执只表示内容已送达语音层的上下文，**不代表已经说给用户听了**。

### 一个容易忽略的事实

文档特别强调：语音和后端是独立运行的。后端任务完成，不等于用户已经听到了答案；用户在任务执行中插话，后端任务也可能还在继续，要不要完成或取消由你的应用决定。

这意味着系统里同时存在三条时间线：**用户说了什么、智能体说了什么、后端做了什么**。在客服和销售场景里，这三者的一致性直接关系到合规风险，例如"智能体已经告诉用户退款成功，但后端其实还没执行"。

## Q4：为什么要拆成三层？

### 结论

三层分别对应三种不同性质的问题：对话体验、任务决策、业务后果。把它们拆开，每一层都可以独立优化、独立替换、独立评测，责任边界也更清楚。

![图 3：语音智能体的三层架构](/img/posts/gpt-live/01-three-layers.svg)

*图 3：用户只和语音层交互；需要决策和工具时委托给 Agent Runtime；真正改变业务状态的动作由 Business Execution 在权限、确认和记录的约束下执行。*

| 层 | 负责什么 | 典型失败 | 怎么评测 |
|---|---|---|---|
| Voice Interface | 听懂、说清楚、轮次自然、处理打断和噪声 | 抢话、冷场、听错数字、语气不当 | 打断率、轮次延迟、识别准确率、主观体验 |
| Agent Runtime | 理解意图、按 SOP 决策、调用工具、维护任务状态 | 选错流程、漏掉规则、工具调用错误 | 决策准确率、SOP 合规率、任务完成率 |
| Business Execution | 在真实系统里执行，并保证权限、确认、幂等和留痕 | 越权操作、重复扣款、无记录可查 | 执行正确率、审计完整性 |

这张表也说明了为什么"业务价值在下面两层"：语音层做得再好，如果 Agent 选错了流程，或者执行层重复下了单，这通电话就是失败的；反过来，语音体验稍差一点，只要事情办对了，用户大多还能接受。

### 为什么执行层必须由应用掌握

OpenAI 的文档在两种委托模式下都明确：权限、确认和业务记录由你的应用负责。这不是技术限制，而是责任划分。任何模型都可能出错，能改变业务状态的动作（退款、下单、改资料）必须经过确定性的代码路径：校验权限、在需要时让用户口头确认、保证重复请求不会重复执行、记录每一步。

## Q5：为什么这比端到端语音模型更有战略意义？

### 结论

纯端到端语音模型把理解、决策、表达都压进一个模型，体验可以很好，但很难保证业务正确性，也很难换掉其中任何一部分。GPT-Live 加 delegation 的设计，让语音模型变成**一个可以连接不同业务 Agent 的入口**。

### 四个理由

**1. 能力可以分开演进。** 语音模型追求的是低延迟和自然度，推理模型追求的是正确性，两者的最优解很不一样。拆开之后，语音层升级不影响业务逻辑，业务 Agent 也可以随时换成更强或更便宜的模型。发布页就建议按任务难度给后端配不同的模型。

**2. 业务逻辑留在开发者手里。** SOP、业务规则、知识库、工具权限，本来就是每家企业最核心、最需要掌控的部分。Client Delegation 让这些全部留在自己的 Agent Runtime 里，语音层只是一个调用方。这对私有化部署和受监管行业尤其重要。

**3. 一个入口，多个 Agent。** 同一个语音层可以根据对话内容，把任务分发给不同的业务 Agent：查询、售后、销售、投诉。语音智能体从"一个模型"变成了"一个平台的前端"。

**4. 可评测、可追溯。** 三层分开后，每一层都有自己的指标和日志。出了问题能定位是"听错了""判断错了"还是"执行错了"，这在端到端模型里几乎做不到。

据 OpenAI 公布，GPT-Live-1 搭配强推理后端，在端到端语音智能体任务基准 Tau3 上排名第一；一个客户从级联架构切换过来后，代码量减少了 80%。前者说明"语音层加强后端"的组合在任务完成上是有效的，后者说明语音层本身吸收了大量原本要手写的轮次管理逻辑。

### 代价与反面意见

这个设计也有明显的成本，需要正视：

- **多一跳的延迟**：复杂任务要等后端返回，语音层只能先用应答或闲聊填补等待时间。用户能接受多长的等待、该说什么来填补，是新的设计问题。
- **上下文同步的负担**：Client Delegation 下，对话状态要由应用自己维护，转写有延迟、没有轮次边界，拼接上下文本身就容易出错。
- **一致性问题**：如上一节所说，"说了什么"和"做了什么"是两条独立的时间线，需要专门的机制对齐。
- **端到端模型仍在进步**：如果未来的端到端模型在工具调用和业务正确性上也足够可靠，分层的优势会被削弱。分层架构的长期价值，更多在于可控性和可替换性，而不只是当前的能力差距。

### 落地时的工程清单

如果在 Client Delegation 上构建客服或销售类语音智能体，至少要解决这些问题：

1. **对话状态机**：基于转写流维护轮次和上下文，明确什么时候触发委托、什么时候忽略附和。
2. **SOP 放在 Runtime**：流程节点和业务规则由 Agent Runtime 判断，语音层只负责把结论说出来。
3. **说与做的账本**：记录每一次委托的输入、Agent 的决策、执行结果，以及智能体实际说给用户的话，用来对账和审计。
4. **确认与幂等**：所有改变业务状态的动作，执行前口头确认，执行时保证幂等。
5. **打断策略**：用户在任务执行中插话时，按任务类型决定是继续、取消还是更新参数。
6. **等待话术**：根据后端的预期耗时，决定用自动应答、`session.commentary.append` 播报进度，还是先用 `session.thinking.append` 静默铺垫。
7. **分层评测**：语音层看体验指标，Runtime 看决策和 SOP 合规，执行层看正确率和审计完整性，三者分别回归。

---

## 总结

GPT-Live 最显眼的是全双工，但它真正改变的是语音智能体的架构分工：语音模型负责把对话做得自然，推理和工具交给可替换的后端，业务后果留在开发者自己的确定性代码里。

**Voice Interface → Agent Runtime → Business Execution** 这条链路里，语音是入口，Agent 是大脑，执行层是责任边界。对做语音智能体的团队来说，竞争力不在于自己训练一个更会说话的模型，而在于背后的 Agent 能不能在真实的业务约束下，把每一通电话的任务正确地办完。
