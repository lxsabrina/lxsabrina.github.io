> 起因很简单：我在 DeepSeek 新开源的推理引擎 DeepInfer 下面问了一句"H200（Hopper，SM90）官方支持吗"，得到一个很专业的回复。为了真正读懂那条回复，我一路往下挖，从 GPU 指令集一直挖到注意力的数学本质。这篇文章把这条路完整走一遍。

## 0. 那条回复说了什么

回复的要点有四个：

1. **当前主分支没有官方支持 H200/SM90。** README 只列出 NVIDIA SM100（要求 CUDA 13）和华为 Ascend 950，benchmark 也只在 SM100 上做过。
2. **编译通过不等于支持。** 构建脚本会拉取 FlashMLA、DeepEP、DeepGEMM、DeepSelect 四个子模块，但没有针对 SM90 的兼容配置。能 build、能 import，都证明不了端到端可用。
3. **社区移植是实验性的。** 已经有人做了 SM90 的移植，但那是社区行为，不代表官方路线。
4. **H200 的测试报告仍然有价值**，前提是记录清楚驱动、CUDA 版本、各子模块的 commit SHA，并且把三类结果分开报告：kernel 编译失败、离线推理的正确性、DSpark 打开和关闭时的差异。

这四句话里藏着一整套知识：什么是 SM90 和 SM100，为什么换一代 GPU 就要重写 kernel，FlashMLA 和 DeepGEMM 到底在算什么，DSpark 又是什么。下面一层层拆开。

先放一张全景图，后面所有内容都是在解释它：

![DeepSeek-V4.1 一次前向与底层算子的对应关系](/img/posts/h200-attention/01-model-kernel-map.svg)

*左边是模型结构，写在推理引擎的代码里；右边是每一步依赖的 GPU 算子库。DeepInfer 在 H200 上的问题，全部出在右边。*

## 1. Hopper 和 Blackwell：为什么换一代 GPU 要重写 kernel

### 1.1 两代架构

Hopper 和 Blackwell 是 NVIDIA 数据中心 GPU 的两代架构：

- **Hopper**：2022 年发布，代表产品 H100、H200、H20，计算能力 9.0，记作 SM90。
- **Blackwell**：2024 年发布，数据中心产品 B200、B300 是 SM100/SM103；消费级的 RTX 50 系列也叫 Blackwell，但它是 SM120，指令集和数据中心版不同。

SM（Streaming Multiprocessor）是 GPU 里的基本计算单元，一张 H200 上有一百多个。SM90、SM100 指的是 SM 的设计版本，编译时写的 `sm_90a`、`sm_100a` 就是对应的编译目标。

### 1.2 kernel 是什么

kernel 是一个同时在成千上万个 GPU 线程上运行的函数。以矩阵乘为例，一个高性能 kernel 大致在做三件事：

1. 把一小块数据从显存（HBM）搬进 SM 内部的高速缓存（shared memory）。Hopper 有专门的 TMA 硬件来做这件事。
2. 用张量核心对这一小块做矩阵乘加。Hopper 用 `wgmma` 指令；Blackwell 换成了 `tcgen05` 指令，并且多了一块叫 TMEM 的张量内存。
3. 累加结果，最后写回显存。

kernel 源码由 `nvcc` 按指定的目标架构编译成机器码，**这份机器码只认那一代架构**。如果源码里直接用了 Blackwell 专属的指令，那它在 Hopper 上根本编译不过；如果构建脚本里没写 `sm_90a`，编译不报错，但运行时会报"没有可用的 kernel 镜像"。最危险的是第三种：编译通过、运行也不报错，但走到了一条错误或未经验证的路径上，算出来的数是错的。这就是"编译通过不等于支持"。

![H200 与 B200 从软件到硬件的对比](/img/posts/h200-attention/02-h200-vs-b200.svg)

*上半部分决定 kernel 能不能在 H200 上编译，下半部分决定编译通过后能跑多快。*

### 1.3 落到 DeepInfer 上

根据社区的公开讨论，几个具体的卡点是：

- **FlashMLA**：上游在 2026 年 9 月 30 日移除了 Hopper 支持，SM90 的注意力 kernel 需要社区自己补。
- **DeepGEMM**：Hopper 版本只覆盖 FP8 的 NT 布局加 FP32 缩放系数，没有 FP4 分支，也不支持 UE8M0 格式的缩放系数，而 DeepInfer 的调用点正好依赖这些。
- **DeepSelect**：需要额外加上 `sm_90a` 的编译目标，top-k 才能在 Hopper 上跑。
- **依赖版本**：有人在 H200 上验证社区分支时，发现其中锁定版本的 Humming 依赖有问题，模型还没跑起来就失败了。

社区的 SM90 移植主要在 H20 上验证过（8 卡和 4 卡 H20-3e 能端到端跑通 DeepSeek-V4.1-Flash）。H200 和 H20 同属 SM90，但 FP8 GEMM 的分块配置只在 H20 上调过，H200 走的是启发式默认值，全模型在 H200 上的表现基本没人报告过。这就是回复里说"H200 报告仍然有价值"的原因。

## 2. FP4 和 FP8：同一份权重，三条数据通路

### 2.1 FP4 是什么

FP4（E2M1 格式）只用 4 位存一个数，正数一共只有 8 个取值：0、0.5、1、1.5、2、3、4、6。要表示更大或更小的数，就让每一小组数共用一个缩放系数 scale，真实值 = FP4 值 × scale。DeepSeek V4 系列的 MoE 专家权重就是这样存的，其余参数用 FP8。

### 2.2 "Blackwell 能直接算 FP4"是什么意思

张量核心只能对它认得的数据格式做乘加。Blackwell 的张量核心里有 FP4 的乘法电路，Hopper 没有，它只认 FP8、FP16/BF16、TF32、INT8。所以在 H200 上，FP4 权重必须先变成 FP8 才能送进张量核心。

![FP4 权重在 B200 和 H200 上的三条数据通路](/img/posts/h200-attention/03-fp4-fp8-path.svg)

*左侧框的宽度代表显存占用。*

FP4 的所有取值都能被 FP8 精确表示，所以这个转换**不损失精度**。比如显存里存着 FP4 的 `3`，这一组的 scale 是 `8`，转换时算出 24，再存成 FP8 送进乘法电路。

### 2.3 H200 上的两个方案

| | 显存占用 | 算力 | 代价 |
|---|---|---|---|
| B200 直接算 FP4 | 1× | FP4 峰值约为 FP8 的两倍 | 无 |
| H200 方案一：存 FP4，片上转 FP8 | 1× | FP8 | 每次计算多一步转换 |
| H200 方案二：直接存 FP8 | 2× | FP8 | 显存和带宽都翻倍 |

社区走的是方案一，而且把转换融合进矩阵乘 kernel 内部：权重以 4 位的体积从显存读进片上缓存，在片上就地转成 FP8 再算（dequant-fused FP8 grouped GEMM）。这样显存带宽上不吃亏。

这个选择背后的逻辑是：大模型 decode 阶段的瓶颈是**从显存搬权重**，不是算力。方案一保住了 4 位的搬运量，decode 基本不受影响；真正吃亏的是计算密集的 prefill 阶段，H200 只能按 FP8 的速率算，这是硬件决定的，软件没法弥补。方案二则让专家权重体积翻倍，原本 4 张 141GB 卡能放下的模型可能就放不下了。

## 3. 注意力的基本功

要看懂 FlashMLA，必须先把注意力本身搞清楚。

### 3.1 注意力是一次"软检索"

做过搜索和推荐的人可以直接这么类比：

| 搜索系统 | 注意力 |
|---|---|
| 用户的 query | 当前 token 的 q（query 向量） |
| 文档里用于匹配的部分 | 每个 token 的 k（key 向量） |
| 文档要返回的内容 | 每个 token 的 v（value 向量） |
| 相关度分数 | q · k |
| 取最相关的一篇返回 | 把所有 v **按相关度加权平均** |

区别在最后一行：搜索是硬选择，注意力是软选择。软选择是为了**可微分**：如果用 top-1，分数在一定范围内变动时输出完全不变，导数为 0，跳变点上导数又不存在，梯度没法告诉参数"该往哪调"；用 softmax 加权，输出随分数连续变化，梯度就能一路传回去。这和推荐召回模型用 softmax 或 sampled softmax 训练是同一个道理。

### 3.2 q、k、v 从哪来

每个 token 在某一层的输入是一个向量 x（DeepSeek-V4.1 里是 5120 维）。三个可学习的参数矩阵把它投影成三种角色：

```
q = x · W_Q        k = x · W_K        v = x · W_V
```

这和双塔模型很像：`W_Q` 像 query 塔，`W_K` 像 item 塔，只是每座"塔"只是一个线性层；`W_V` 是双塔里没有的，它决定被匹配上之后要交出什么内容。

关键点在于：**token i 的 q 来自 `x_i`，token j 的 k 和 v 来自 `x_j`**。同一个序列里的每个 token，既是提问者，也是被检索的文档，这就是"自注意力"。

### 3.3 一个 query 的三步

对第 i 个 token：

1. **打分**：`s_ij = q_i · k_j ÷ √d`
2. **归一化**：`p_ij = e^(s_ij) ÷ Σ_j e^(s_ij)`
3. **加权平均**：`o_i = Σ_j p_ij · v_j`

除以 √d 是因为点积的方差随维度 d 增长，不除的话 softmax 会变得极尖，梯度消失。用 e 的指数是为了把任意实数变成正数权重并放大差距；除以总和是为了让权重和为 1。

N 个 token 一起算，就是矩阵形式：

![注意力的矩阵形状](/img/posts/h200-attention/04-attention-shapes.svg)

*S = QKᵀ 必然是 N×N：每个 token 都要和每个 token 打一次分。*

几个补充：

- **因果遮挡**：生成模型里 token i 不能看后面的 token，S 的右上三角设成 −∞，权重为 0。
- **多头**：把 q、k、v 切成多份，每份独立做一遍注意力再拼起来。V4.1 有 64 个注意力头，但只有 1 个 KV 头，即 64 个 query 头共用同一份 k、v。
- **KV cache**：前面 token 的 k、v 不会再变，算一次就缓存。q 不需要缓存，因为旧 token 的 q 只在它自己那一步用过。

### 3.4 prefill 和 decode

- **prefill**：一次处理整段输入，N 个 query 同时算，是完整的 N×N。
- **decode**：每次只生成一个新 token，只有 1 个 q，却要把整个 KV cache 从显存读一遍。计算量很小，瓶颈是**读显存的带宽**。

这一点贯穿全文：decode 阶段几乎所有优化，都是在想办法少读、读快。

## 4. FlashAttention：为什么注意力允许"流式"计算

### 4.1 问题出在显存读写

GPU 里有两种存储：显存容量大但慢，片上缓存（SRAM）快得多但每个 SM 只有几百 KB。

普通写法把三步当成三个独立算子，每一步的中间结果都写回显存、下一步再读出来。中间结果 S 和 P 都是 N×N，上下文 10 万 token 时就是 100 亿个元素，用 BF16 存一张就要 20GB，而且这只是一个头、一层。

![普通注意力与 FlashAttention 的显存读写对比](/img/posts/h200-attention/05-memory-traffic.svg)

FlashAttention 的做法是把 Q 和 K、V 都切成小块，在片上缓存里把"打分 → softmax → 乘 V"一口气做完，S 和 P 从头到尾不需要完整存在。

这里有一个关键问题：softmax 的分母要等整行分数都算完才知道，凭什么能一块一块地算？

### 4.2 核心推导：分子、分母都是求和

把输出写开：

```
o_i = Σ_j p_ij · v_j = ( Σ_j e^(s_ij) · v_j ) ÷ ( Σ_j e^(s_ij) )
```

分子和分母都是**对 j 求和**。求和可以分批做，先加一部分、再加一部分，结果不变。所以对一行来说，只需要维护两个累加量：

- **l**：分母的累加，Σ e^s
- **O**：分子的累加，Σ e^s · v

K、V 每进来一块，就往 l 和 O 上加一点，然后这块就可以丢掉。最后 O ÷ l 就是答案。

### 4.3 唯一的麻烦：数值溢出

e 的指数会溢出：e^11 就已经超过 FP16 的上限 65504。标准做法是减去最大值 m，算 e^(s − m)，让所有项都 ≤ 1，最后分子分母同时带着 e^(−m)，相除时抵消。

但 m 要看完整行才知道。解决办法是先用"目前见过的最大值"，遇到更大的再修正：之前累加的每一项都是 e^(s − m旧)，乘上 e^(m旧 − m新) 就变成了 e^(s − m新)。因为 l 和 O 都是这些项的和，**整体乘一次**就行。

可以把它理解成"换单位"：一直用"万元"记账，突然来了一笔大钱改用"亿元"，之前的总数要整体除以一万。

### 4.4 走一遍数字

一个 query 对 8 个 key 的分数和对应的 v（v 简化成一个数）：

| key | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| 分数 s | 1.2 | 0.3 | 2.1 | −0.5 | 0.8 | 3.0 | 0.1 | 1.5 |
| v | 2 | −1 | 4 | 0 | 3 | 1 | −2 | 5 |

每 2 个 key 一块，分 4 块读入：

![在线 softmax 的逐块累加](/img/posts/h200-attention/06-online-softmax.svg)

*横条总长就是 l。块 1 和块 2 都出现了更大的分数，旧段整体乘 0.41 缩短（这组数字恰好每次都差 0.9，是巧合）；块 3 最大值没变，不用缩放。*

如果先不管 m，直接用 e^s 当权重累加，最后的分母是 41.34、分子是 84.92，相除得 2.054；带 m 的版本里每一步的 l 和 O，恰好就是这两个数除以 e^(当前 m)。两种算法的最终结果和一次性做 softmax 完全一致，都是 2.054。

### 4.5 三个性质

总结一下，注意力能被 FlashAttention 这样算，靠的是三个性质：

1. **行与行独立**：第 i 行只依赖 `q_i` 和所有 k、v，所以可以把 Q 按行切块，交给不同的 SM 并行算。
2. **分子分母都是求和**：所以一行之内，K、V 可以一块一块流式处理。如果 softmax 依赖的是整行的中位数之类的统计量，这一步就做不了。
3. **溢出可以事后修正**：最大值变化时，旧的累加量乘一个系数就能换到新基准。

需要注意：N×N 的中间矩阵只在 prefill 时出现。decode 时只有一行 query，分数是 1×N，省不了多少中间矩阵；那时的瓶颈是读 KV cache，这正是 FlashMLA 要解决的。

## 5. FlashMLA：在压缩向量上做注意力

### 5.1 MLA 的吸收技巧

以 DeepSeek V3 公开的 MLA 设计为例（V4 系列在此基础上又改过，细节可能不同）：KV cache 里每个 token 只存一个压缩向量 `c_j`（512 维，外加 64 维位置编码部分），真正的 k、v 需要用矩阵还原：`k_j` = `W_UK` · `c_j`，`v_j` = `W_UV` · `c_j`。

如果每次都先还原再算，就白压缩了。MLA 的技巧是**把还原矩阵吸收进 q 和输出**：

```
打分：q_i · k_j = q_i · (W_UK · c_j) = (W_UKᵀ · q_i) · c_j
输出：Σ_j p_ij · v_j = W_UV · ( Σ_j p_ij · c_j )
```

先把 q 变换一下，就能直接和压缩向量点积；输出先在压缩空间做加权平均，最后再乘一次 `W_UV`。结果是：**`c_j` 同时充当 k 和 v，所有头共用同一份**。这也解释了为什么 V4.1 只有 1 个 KV 头。

### 5.2 一个 SM 里的循环

decode 时一个请求的计算形状是：64 个头的 q（相当于 64 行 query）对 N 个压缩向量。一个 SM 里的循环大致是：

1. 用 TMA 从显存搬一页压缩向量进片上缓存。KV cache 是分页存放的，要按页表找到每一页的位置。
2. 张量核心算出 64 个头对这一页 token 的分数。
3. 每个头一行，做第 4 节的在线 softmax，更新 m、l、O。
4. **同一页压缩向量再拿来当 V 用**，乘权重累加进 O。k 和 v 是同一份数据，只搬一次、用两次，省一半读带宽。
5. 下一页，直到读完。

V4.1 在此基础上又加了一个 indexer：一个小的辅助注意力先给压缩条目打分，每个 query 只保留最相关的 512 个（前面还有一级候选筛选）。kernel 因此还要支持"只读被选中的那些块"的稀疏读取。

### 5.3 一张卡里多个 SM：split-KV

decode 时一个请求只有一行 query，如果只让一个 SM 从头读到尾，其他一百多个 SM 都闲着。所以 FlashMLA 把一个请求的 KV cache 切成几段，分给多个 SM：

![FlashMLA 的 split-KV 与合并](/img/posts/h200-attention/07-flashmla-split-kv.svg)

每个 SM 只算自己那段的局部 m、l、O，合并时找出全局最大的 m，把每段的 l 和 O 换到同一个单位再相加。这和第 4 节的流式累加是同一个数学性质，只是从"按时间先后加"变成了"并行算完再加"。FlashMLA 的接口里先调用一次 `get_mla_metadata`，就是根据每个请求的长度事先决定怎么切分，让各个 SM 的工作量均匀。

### 5.4 多张卡之间

decode 时多卡通常对注意力做数据并行：每张卡负责一部分请求，这些请求的 KV cache 完整地放在本卡，注意力不跨卡交换 K、V。上下文长到一张卡放不下时，才会用上下文并行（CP），把同一个请求的 KV cache 按 token 切到几张卡上，每张卡算局部的 m、l、O，再跨卡合并，方法完全一样。

从 SM 内的分块循环，到 SM 之间的 split-KV，再到卡之间的上下文并行，用的都是同一个性质：**softmax 加权平均能拆成分子、分母两个求和，分开算、换单位、再相加**。

## 6. MoE：路由、分发、计算、汇总

### 6.1 一层 MoE 的四步

V4.1 的每层 MoE 有 384 个路由专家和 1 个共享专家，每个 token 选 6 个。专家分散在不同 GPU 上（专家并行），所以每一层都要：

1. **路由**：一个小线性层给 384 个专家打分，取前 6 个，并算出各自的权重。DeepSelect 提供 top-k kernel，我推测它用在这一步。
2. **分发（dispatch）**：把 token 发给持有这些专家的 GPU。实际是整个 batch 里所有 GPU 互相交换 token 的 all-to-all，机内走 NVLink，跨机走 RDMA，这是 DeepEP 的工作。
3. **专家计算**：每张卡把收到的 token 按专家分组，每个专家做自己的矩阵乘，由 DeepGEMM 完成。
4. **汇总（combine）**：结果沿原路发回，每个 token 把自己 6 个专家的输出按路由权重加起来，再加上共享专家的输出。也是 DeepEP 的工作。

![一个 token 在一层 MoE 里的分发与汇总](/img/posts/h200-attention/08-moe-dispatch.svg)

### 6.2 DeepGEMM 为什么要专门写

GEMM 即通用矩阵乘。不用 cuBLAS 这类现成库，主要因为：

- **低精度加分组缩放**：要在 kernel 内部处理 FP8/FP4 以及"每组数据配一个 scale"。
- **grouped GEMM**：每个专家分到的 token 数不一样，有的很多、有的很少，要在一次 kernel 启动里算完所有大小不一的矩阵乘，而不是每个专家启动一次。
- **融合**：DeepInfer 里还有把多步融合在一起的 mega-kernel，Hopper 上没有对应实现，只能退化成非融合版本。

### 6.3 专家是怎么"分工"出来的

专家不是人为分配的。设计时只规定"这一层有 384 个结构相同的小前馈网络和一个路由器"，参数随机初始化。训练时每个 token 只激活被选中的专家，反向传播也只有它们收到梯度。某个专家碰巧对某类 token 处理得好一点，路由器就更倾向于把这类 token 发给它，正反馈之下专家逐渐分化。

为了避免少数专家被选得越来越多、其余专家闲置，训练时要做负载均衡。DeepSeek V3 的做法是给每个专家的路由分数加一个可调偏置，被选太多的调低，太少的调高。分化的结果通常不是"数学专家""历史专家"这种干净的主题划分，而是更细碎、偏语言层面的分工。

## 7. 一层里的分工：注意力搬运，MoE 加工

### 7.1 为什么不能只有注意力

注意力的输出 `o_i` 永远是各个 v 的加权平均，它能决定"从谁那里拿多少"，但拿来的东西本身没有被改变。

![一层里注意力与 MoE 的分工](/img/posts/h200-attention/09-attention-vs-moe.svg)

*注意力是整个模型里唯一让 token 之间交换信息的地方；MoE 在每个 token 上独立工作，不看别人。*

这带来两个问题：

1. **混合不等于理解**："不好"里，"好"的位置取到"不"的信息，得到的是夹在"不"和"好"之间的模糊向量，它不会自动变成"坏"。要从"否定 + 正面"得出"负面"，需要非线性变换。而且如果每层只做线性混合，叠 40 层和叠 1 层本质上差不多，深度失去意义。
2. **上下文里没有的东西拿不到**：问"巴黎是哪国首都"，上下文里没有"法国"，注意力从哪都取不到。这类知识存在参数里，主要在前馈层，模型的大部分参数也在这里。

所以每层是两步：注意力像开会，听别人发言、记下相关的；MoE 像会后回到座位上查资料、把信息想清楚。

### 7.2 非线性到底提供了什么

把情感问题简化成两个 0/1 特征：p 表示有没有正面词，n 表示有没有否定词。

| 词组 | n | p | 最终情感 |
|---|---|---|---|
| 坏 | 0 | 0 | 负 |
| 好 | 0 | 1 | 正 |
| 不坏 | 1 | 0 | 正 |
| 不好 | 1 | 1 | 负 |

线性函数 a·p + b·n + c 做不到：比较"坏"和"好"要求 a > 0，比较"不坏"和"不好"要求 a < 0，矛盾。这是经典的异或问题，和广告 CTR 模型里"逻辑回归学不到特征交叉"是一回事。

用 ReLU（负数截断为 0）造两个隐藏单元：h1 = ReLU(p − n)，h2 = ReLU(n − p)，输出 h1 + h2。代入四种情况：好 → 1，不坏 → 1，坏 → 0，不好 → 0，全部正确。

![线性分不开“不好/不坏”，ReLU 的两个开关可以](/img/posts/h200-attention/10-xor-relu.svg)

截断提供了"如果条件不满足就输出 0"，也就是"如果"。现在的模型用 SwiGLU：

```
FFN(x) = W2 · ( SiLU(W1 · x) ⊙ (W3 · x) )
```

SiLU 是平滑版的 ReLU，起开关作用；⊙ 是逐元素相乘，两个数都大时乘积才大，这本身就是"A 且 B"。W1·x 检测一种模式，W3·x 检测另一种，相乘得到"同时出现"，W2 再把组合映射成输出方向。vLLM 加载 DeepSeek V4 时把 checkpoint 里的 `w1`、`w3` 合并成一个 `gate_up_proj`，就是为了一次矩阵乘同时算出这两路。

### 7.3 残差流

每层结束时：

```
x ← x + attention(x)
x ← x + moe(x)
```

所以 x 是一块所有层共用的"黑板"：第 1 层时它只是 token 自己的 embedding，之后每层都往上写一点，注意力写从上下文收集来的信息，MoE 写加工后的特征和从参数里取出的知识。`o_i` 是这一层新收集的，`x_i` 是到这一层为止积累的全部理解。同一个"她"放在不同句子里，几层之后的向量就完全不同了。

## 8. 从最后一个向量到下一个 token

![从最后一个 token 的向量到下一个 token 的生成循环](/img/posts/h200-attention/12-next-token-loop.svg)

1. 只取最后一个位置的向量。因果遮挡下，它是唯一看过全部上下文的位置，训练时它的任务就是预测下一个词。
2. 经过最后一次归一化，乘输出矩阵（LM head，大小 5120 × 129,280），得到每个词的分数。这和召回一样：一个向量和整个词表做点积。
3. softmax 变成概率，再按贪心、温度采样或 top-p 选出一个 token。
4. 新 token 查 embedding，再过 40 层。这次只算这一个新位置：它的 q 读 KV cache 里所有旧 token 的 k、v，同时把自己的 k、v 追加进去。

注意 LM head 只是一个线性层，真正的"思考"都在前面 40 层完成了。训练时每个位置都在预测自己的下一个词，一条 1000 token 的样本一次提供 999 个练习；推理时 prefill 也会算出每个位置的分数，但只用最后一个。

**DSpark** 就在这里起作用：它是附加在模型上的多 token 草稿头，用最后的向量一次猜出后面好几个 token，主模型再把这些猜测当作新 token 一次性过一遍 40 层来验证，猜对的保留。验证机制保证输出与不用它时一致，只是更快。V4 Flash 的仓库带上 DSpark 后总参数从 284B 变成 304B，可见它和主模型存在同一个 checkpoint 里，只是参数名前缀不同。

这也解释了回复里为什么要求"DSpark 开/关分开报告"：开启后输出应该和关闭时完全一致；如果不一致，或者草稿的接受率异常低，往往说明 H200 上某个 kernel 的数值有问题。这是一个很便宜的正确性探针。

## 9. 5120 维为什么够用

这是我在这条路上最惊讶的问题：一个 token 只有 5120 个数，为什么能表达那么复杂的语义？

### 9.1 概念是方向，不是维度

如果每一维代表一个特征，5120 个当然不够。但模型不是这么用的：一个概念对应空间里的一个**方向**（5120 个数按某种比例组合）。问题于是变成，5120 维空间里能放多少个互相几乎不干扰的方向？

高维空间有一个反直觉的性质：随便取两个方向，它们几乎一定接近垂直。我对每个维度随机抽了 2 万对方向，统计夹角余弦：

![随机方向两两夹角的余弦分布随维度变化](/img/posts/h200-attention/11-cosine-dimension.svg)

| 维度 | 典型 \|cos\| | 相当于夹角 | \|cos\| > 0.1 的比例 |
|---|---|---|---|
| 2 | 0.634 | 约 51° | 94% |
| 10 | 0.259 | 约 75° | 77% |
| 100 | 0.080 | 约 85° | 32% |
| 5120 | 0.011 | 约 89° | 0% |

如果允许方向之间有少量重叠，能塞进去的方向数随维数**指数增长**，远多于 5120。模型利用这一点把远多于维数的特征"叠放"在同一个空间里，可解释性研究里称为**叠加（superposition）**；用稀疏自编码器去分解大模型的中间向量，能找出几百万个可解释的特征。

叠加能成立有一个前提：**特征是稀疏的**，同一时刻只有少数特征激活。语言恰好满足这一点，一句讲做饭的话里，"量子力学""法律条款"这些特征几乎都是 0。

### 9.2 一个向量不需要装下全部

信息实际分布在三个地方：

| 存在哪 | 存什么 |
|---|---|
| 每个位置的向量（5120 维 × 上下文长度 × 40 层） | 对当前这段话的理解，"工作记忆" |
| 模型参数（几千亿个数） | 世界知识和语言规律，"长期记忆" |
| KV cache | 前文每个 token 的 k、v，随时可检索 |

所以单个向量更像一个查询加一个指针，而不是一本百科全书。推荐系统里几十到几百维的用户向量能在几百万 item 里找到合适的，也是同样的道理。

### 9.3 信息量上的量级对比

一个 5120 维 BF16 向量的原始容量是 5120 × 16 = 81,920 比特，而从 12.9 万个词里选一个只需要约 17 比特。这只是理论上限，模型实际能用的容量要小得多：后面的层只能通过投影（点积）读取信息，信息必须以"某个方向上的投影大小"存放，不能藏在第五位小数里（BF16 本来也只有两三位有效数字）；而且为了扛住叠加带来的串扰，每个特征都要存得冗余。所以这个对比只说明容量大概率不是瓶颈，不是证明。

### 9.4 维度实际是怎么定的

规模定律（OpenAI 2020、DeepMind Chinchilla 2022）的经验是：模型效果主要取决于总参数量、数据量和算力，在相当大的范围内宽度和深度怎么分配影响不大。所以设计者先定算力预算，再在工程约束下取舍宽度：

- 加宽：每层计算量大约随 d² 增长，KV cache 变大，但更好并行、更好切分到多卡。
- 加深：层是串行的，延迟线性增加。
- 硬件对齐：维度通常取 128 的倍数，5120 = 128 × 40。

所以不同规模的模型宽度不同，DeepSeek-V3 是 7168，V4.1 Flash 作为新架构里最小的型号用 5120。"够用"的准确含义是：再加宽的收益，不如把同样的算力花在更多层、更多专家或更多数据上。

它也有不够的时候：宽度和参数越小，能可靠存储的冷门知识越少，叠加串扰越容易导致幻觉，长上下文里的细节也更容易丢。

## 10. 回到 H200：一份有价值的测试报告长什么样

绕了一大圈，再回头看那条回复，每一句都有了具体含义。如果要在 H200 上试 DeepInfer 的社区分支，一份对维护者有用的报告应该包含：

**环境（可复现性）**

- 驱动版本（`nvidia-smi`）、CUDA 版本（`nvcc --version`）、GCC 和 Python 版本
- DeepInfer 分支和 commit，FlashMLA、DeepGEMM、DeepEP、DeepSelect 以及 Humming 等依赖各自的 commit SHA
- 卡数、互联方式（NVLink 拓扑）

**第一层：kernel 编译**

- 每个子模块单独编译、单独跑自带的单元测试，记录哪个失败、报的是什么错
- 区分三类失败：架构列表里没有 `sm_90`、nvcc 报指令或模板错误、编译通过但运行时报错

**第二层：离线推理正确性**

- 固定输入、固定采样参数（贪心），与 H20 或 SM100 上的输出逐 token 比对
- 跑一个小评测集（比如 GSM8K 子集）看分数是否正常

**第三层：DSpark 开/关对比**

- 两种模式在贪心解码下输出应完全一致
- 记录草稿接受率和端到端吞吐、TTFT

**性能（可选）**

- 不同 batch、不同上下文长度下的 tokens/s
- FP8 GEMM 是否用的启发式配置，是否值得为 H200 单独调优

从一句"H200 支持吗"出发，最后落到一张可以执行的检查表，这大概就是追问到底的价值。
